## 1. 한눈에 보기

```
홍보(인스타그램 · 블로그 · 박람회 QR · 검색 …)
   │  링크에 UTM 표시
   ▼
홈페이지 방문 ──────────────▶ GA4: 방문 · 채널 · 캠페인 · 나라 · 페이지 (익명, 전체 흐름)
   │  브라우저가 유입을 기억(첫 방문 6개월 · 최근 유입 90일)
   ▼
문의 폼 제출 ───┬──────────▶ GA4: contact_start → generate_lead (익명, 접수 번호 포함)
               └──────────▶ 문의 메일: 제목 + 본문 끝 [접수 정보] (한 건 단위, 접수 번호 포함)
   ▼
영업 결과 기록(시트) ───────▶ 접수 번호로 메일 · GA4와 이어 "홍보 → 문의 → 계약"을 한 줄로
```

- **GA4**는 많은 방문을 익명으로 모아 비율과 추세를 봅니다. 이름 · 이메일 · 소속은 보내지 않습니다.
- **문의 메일**은 한 건 한 건이 어디서 왔는지 봅니다. 공공 영업은 문의 수가 적고 한 건이 크므로 이쪽이 더 중요합니다.
- **접수 번호**(`WS-261015-7K2Q`)가 둘을 잇습니다. 메일 본문과 GA4 이벤트에 같은 번호가 들어갑니다.
- 코드: `src/scripts/attribution.ts`(유입 기억 · GA4 이벤트), `src/scripts/contact-form.ts`(문의 폼).

## 2. 링크에 붙이는 표시(UTM)

사이트 밖에서 홈페이지로 오는 링크에는 아래 표시를 붙입니다. 붙이지 않으면 GA4와 문의 메일에서 "직접 방문"이나 "인스타그램"처럼 뭉뚱그려져, 어느 게시물 · 어느 행사 덕인지 나눌 수 없습니다.

| 어디서 | 붙이는 값 |
|---|---|
| 인스타그램 프로필 | `links.html`에 이미 들어 있음 (`utm_source=instagram&utm_medium=social&utm_campaign=bio`) |
| 인스타그램 게시물 · 스토리 | `?utm_source=instagram&utm_medium=social&utm_campaign=<기사 id>` |
| 블로그 본문 | `?utm_source=blog&utm_medium=referral&utm_campaign=<기사 id>` |
| 박람회 QR · 인쇄물 | `?utm_source=fair&utm_medium=print&utm_campaign=<행사-연도>&utm_content=<놓인 곳>` |
| 카탈로그 PDF 속 링크 · QR | `?utm_source=catalog&utm_medium=print&utm_campaign=catalog-2026` |
| 명함 QR | `?utm_source=card&utm_medium=print&utm_campaign=namecard` |
| 이메일 서명 | `?utm_source=email&utm_medium=email&utm_campaign=signature` |
| 뉴스레터 · 단체 메일 | `?utm_source=newsletter&utm_medium=email&utm_campaign=<보낸 날-주제>` |
| 보도자료 속 링크 | `?utm_source=<매체 영문명>&utm_medium=press&utm_campaign=<기사 id>` |
| LinkedIn · Zalo | `?utm_source=linkedin`(또는 `zalo`)`&utm_medium=social&utm_campaign=<기사 id>` |

**이름 규칙**

- 영문 소문자, 띄어쓰기 대신 하이픈(`-`). 행사는 `이름-연도`(`vietedu-2026`, `edtech-korea-2026`).
- 한 번 쓴 이름은 바꾸지 않습니다. `VIETEDU`와 `vietedu`처럼 한 글자만 달라도 GA4에서 다른 줄로 갈라집니다(대소문자는 사이트가 소문자로 맞추지만, 철자는 맞출 수 없습니다).
- `utm_content`는 같은 행사 안에서 놓인 곳을 나눌 때만: `banner`(부스 배너), `brochure`(리플릿), `booth`(상담 데스크).
- `utm_source`가 `instagram` · `blog` · `fair`(또는 `ig` · `naver_blog` · `event`)이면 문의 폼의 '유입 경로'가 미리 골라집니다. 메일에는 "(방문 경로로 미리 선택됨)"이라고 적혀, 방문자가 직접 고른 답과 구분됩니다.

**문의 폼으로 바로 보내는 링크**: 주소에 `purpose`(`consult` 도입 상담 · `demo` 시연 요청 · `partner` 파트너십·해외)와 `product`(`lecognizer` · `lecognizer-ai` · `learnhubble`)를 붙이면 그 목적이 골라진 채로 열립니다.

## 3. 문의 메일 읽는 법

**제목**: `[웹 문의 · 목적 · 관심 제품 · 언어] 소속 · 이름`

```
[웹 문의 · 시연 요청] 서울시교육청 · 홍길동
[웹 문의 · 시연 요청 · LearnHubble AI · EN] Hanoi University · Nguyen Van A
[웹 문의] ○○대학교 · 김○○                      ← 목적을 고르지 않음
```

- 모든 제목이 `[웹 문의`로 시작합니다. 메일함 규칙은 이것으로 거릅니다(옛 제목 `Contact Us 문의 접수`로 걸러 두었다면 바꿉니다).
- 목적 · 제품 · 언어는 있을 때만 붙습니다. 언어가 없으면 한국어 페이지에서 온 문의입니다.

**본문 끝의 접수 정보**(문의한 사람이 적은 글 아래에 홈페이지가 붙입니다)

```
----------------------------------------
[접수 정보] 홈페이지가 자동으로 붙인 정보입니다.
접수 번호: WS-261015-7K2Q
문의 목적: 시연 요청
관심 제품: LearnHubble AI
문의 언어: 영어 (/en/contact.html)
문의한 곳: 제품 · LearnHubble AI 시연 요청 (product#learnhubble)
이번 유입: fair / print / vietedu-2026 · brochure (2026-10-15, 첫 페이지 /en/index.html)
첫 방문: 2026-09-20 · google / organic (첫 페이지 /en/index.html)
유입 경로(응답): 박람회·행사 (방문 경로로 미리 선택됨)
```

| 줄 | 뜻 |
|---|---|
| 접수 번호 | 이 문의의 번호. GA4 이벤트와 영업 결과 시트에서 같은 번호로 찾습니다 |
| 문의 목적 · 관심 제품 | 폼 위 카드에서 고른 목적. 제품은 제품별 버튼(예: LearnHubble AI 시연 요청)으로 왔을 때만 |
| 문의한 곳 | 문의로 오기 직전에 누른 버튼(페이지 · 영역). "문의 칸에서 바로"는 버튼 없이 폼을 쓴 경우 |
| 이번 유입 | 이번 방문을 만든 유입 `출처 / 매체 / 캠페인`. 이번에 주소를 직접 쳐서 왔으면 90일 안의 최근 유입을 쓰고 "이번에는 직접 방문"을 붙입니다(GA4와 같은 방식) |
| 첫 방문 | 이 브라우저로 처음 들어온 날과 유입(6개월 안). "검색으로 알게 되어, 나중에 박람회를 보고 문의" 같은 흐름이 보입니다 |
| 유입 경로(응답) | 방문자가 폼에서 직접 고른 답. 박람회 · 지인 추천 · 공문처럼 링크로 추적되지 않는 경로를 알려 줍니다 |

출처 이름: `google` · `naver` · `daum` · `bing` · `coccoc`(검색, 매체 `organic`), `instagram` · `facebook` · `linkedin` · `youtube` · `kakao` · `zalo`(매체 `social`), 네이버 블로그는 `blog`, 그 밖의 사이트는 그 주소(매체 `referral`), UTM이 있으면 UTM 값 그대로.

**설정 현황(2026-09-27)**

| | 항목 | 상태 |
|---|---|---|
| 1 | 운영 배포에서 GA 켜기 | 남음: 운영 호스팅을 정할 때 |

| 6 | 향상된 측정(양식 상호작용 끔) | 완료 |
| 7 | Search Console 연결(선택) | 진행 중: 도메인 속성만 추가, 소유 확인 전(아래 '이어서 할 일') |

**이어서 할 일(사무실에서, 2026-09-27 기준)**

- **Search Console 소유 확인**: wickedstorm.inc@gmail.com 계정의 Search Console에 도메인 속성 `wickedstorm.kr`을 추가해 두었습니다(확인 전). 첫 화면의 "이미 확인을 시작하셨나요? 절차를 마무리하세요."로 이어서 엽니다. 방법은 둘 중 하나입니다.
  - **DNS(권장, www 포함 도메인 전체)**: DNS는 AWS Route 53에 있습니다(네임서버 `awsdns`, 등록대행 가비아). 호스팅 영역 `wickedstorm.kr`의 기존 TXT 레코드(`"v=spf1 include:_spf.daum.net ~all"`, 메일용이니 지우지 않음)를 **편집해 한 줄 더합니다**: `"google-site-verification=a0xNdujyBJ6n4nJx_j47OfeXjqRHBSXgtJahdJ0ocN4"`. 반영되면 Search Console에서 '확인'. 기존 IAM 로그인이 막혀 있어, AWS 관리자에게 계정 복구 또는 레코드 추가를 요청해야 합니다.
  - **GA 태그로(AWS 없이)**: '웹사이트 추가' → **URL 접두어**에 사이트 주소(`https://www.wickedstorm.kr/`, 새 사이트가 www 없이 열리면 `https://wickedstorm.kr/`도)를 넣고 확인 방법 **Google 애널리틱스**. 주소가 여러 개면 주소마다 따로 추가합니다.
  - 확인되면: GA4 관리 → 제품 링크 → Search Console 링크 → 연결 → 방금 확인한 속성 → 웹 스트림 "홈페이지".
- **사무실 IP**: 사무실 인터넷에서 [api.ipify.org](https://api.ipify.org)로 공인 IP를 보고 아래 5번대로 등록합니다(2026-09-27 카페의 112.168.70.7은 사무실 IP가 아님).

1. **운영 배포에서 GA 켜기**: 운영 사이트를 빌드할 때 환경 변수 `PUBLIC_GA_ID=G-0Y5QD1HBGN`을 넣습니다(`site.config.mjs`). 미리보기 · 점검 빌드에는 넣지 않습니다(통계가 섞이지 않게).
2. **데이터 보관 14개월**: 관리 → 데이터 수집 및 수정 → 데이터 보관 → 이벤트 데이터의 데이터 보관 `14개월` → 저장. 기본값은 2개월이라, 그대로 두면 작년 박람회와 비교할 수 없습니다(개인정보처리방침의 "최대 14개월"과 같습니다). 표준 GA4에서 고를 수 있는 가장 긴 기간입니다.
3. **문의를 주요 이벤트로**: 관리 → 데이터 표시 → 이벤트 → **이벤트 만들기** → 이벤트 이름 `generate_lead`, "주요 이벤트로 표시" 켜기, 이벤트 생성 방법 **코드로 만들기** → 만들기. 사이트 코드가 보내는 이벤트를 이름으로 미리 등록하는 방식입니다(아직 한 번도 들어오지 않은 이벤트는 목록의 별표로 표시할 수 없습니다). 기본 값은 두지 않고, 계산 방법은 "이벤트당 한 번"(문의 한 건 = 한 번). 이제 보고서마다 "주요 이벤트" 열에 문의 수가 나옵니다.
4. **맞춤 측정기준 6개**: 관리 → 데이터 표시 → 맞춤 정의 → 맞춤 측정기준 만들기. 범위는 모두 "이벤트". 이벤트 매개변수는 아직 들어온 적이 없어 목록에 없으므로 이름을 직접 적습니다.

   | 측정기준 이름 | 이벤트 매개변수 | 값 |
   |---|---|---|
   | 문의 목적 | `purpose` | consult · demo · partner · general(고르지 않음) |
   | 관심 제품 | `product` | lecognizer · lecognizer-ai · learnhubble |
   | 문의한 곳 | `entry` | `페이지#영역` (예: product#learnhubble, home#header, contact#form) |
   | 유입 경로 응답 | `traffic` | direct · portal · instagram · blog · event · job_posting · news · referral · etc |
   | 접수 번호 | `lead_id` | WS-YYMMDD-XXXX |
   | 문의 언어 | `form_lang` | ko · en · ja · vi |

   등록한 뒤에 들어온 데이터부터 보입니다. 접수 번호는 값이 문의마다 다르지만 한 달에 문의 수만큼만 생겨 보고서에 부담이 없습니다(GA4가 "고유 값이 많은 측정기준" 경고를 띄웁니다).
5. **사무실 방문 빼기**: 관리 → 데이터 수집 및 수정 → 데이터 스트림 → 웹 스트림 "홈페이지" → 태그 설정 구성 → 설정 더보기 → 내부 트래픽 정의에 사무실 공인 IP를 넣고, 관리 → 데이터 수집 및 수정 → 데이터 필터 → Internal Traffic을 "활성"으로 바꿉니다. 직원이 사이트를 확인하는 방문이 통계에 섞이지 않습니다. 활성으로 바꾼 뒤 걸러진 방문은 되돌릴 수 없으니 IP를 확인하고 켭니다(사무실 인터넷에서 [api.ipify.org](https://api.ipify.org)를 열면 공인 IP가 보입니다).
6. **향상된 측정**: 관리 → 데이터 수집 및 수정 → 데이터 스트림 → 웹 스트림 "홈페이지" → 향상된 측정 구성(톱니바퀴) → 저장. "파일 다운로드"(카탈로그 PDF)와 "이탈 클릭"(솔루션 사이트로 나가는 클릭)은 켜 둡니다. "양식 상호작용"은 끕니다. 문의 폼은 우리가 보내는 `contact_start` · `generate_lead`로 보고, 자동 양식 이벤트는 오류로 막힌 제출도 세어 숫자를 흐립니다.
7. **Search Console 연결**(선택): 관리 → 제품 링크 → Search Console 링크 → 연결. 먼저 [Search Console](https://search.google.com/search-console)에 `wickedstorm.kr`을 등록하고 소유를 확인해야 목록에 나옵니다(도메인 속성, DNS TXT 레코드로 확인하면 www와 하위 경로가 모두 들어갑니다). 구글에서 어떤 검색어로 들어왔는지는 GA4가 아니라 Search Console에만 있습니다.

## 5. GA4에서 보는 법

왼쪽 메뉴 **보고서**는 정해진 표, **탐색**은 직접 짜는 표입니다. 날짜는 오른쪽 위에서 고릅니다. 보고서 메뉴의 묶음 이름(수명 주기 등)은 속성에 따라 조금 다를 수 있습니다.

| 알고 싶은 것 | 보는 곳 |
|---|---|
| 어느 채널(검색 · SNS · 직접 · 추천)이 방문과 문의를 가져오나 | 보고서 → 획득 → **트래픽 획득**. 표의 기준은 "세션 기본 채널 그룹". "주요 이벤트" 열을 `generate_lead`로 고르면 채널별 문의 수, "세션 주요 이벤트 비율"이 문의 전환율 |
| 캠페인별(VIETEDU, 인스타 게시물 …) 성과 | 같은 표에서 기준을 **세션 캠페인** 또는 **세션 소스/매체**로 바꾸기 |
| 처음 알게 된 경로 | 보고서 → 획득 → **사용자 획득**(첫 사용자 기준) |
| 목적별 문의 수, 어느 버튼이 문의를 만드나 | 탐색 → 자유 형식. 측정기준에 "문의 목적" · "문의한 곳", 측정항목 "이벤트 수", 필터 "이벤트 이름 = generate_lead" |
| 폼을 쓰기 시작한 사람 중 몇 %가 보냈나 | 탐색 → 유입경로 탐색. 1단계 `contact_start`, 2단계 `generate_lead` |
| 문의 전에 어떤 페이지를 봤나 | 탐색 → 경로 탐색. 끝점을 `generate_lead`로 두고 거꾸로 보기 |
| 나라별 방문(하노이 박람회 전후 베트남) | 보고서 → 사용자 → 사용자 속성 → 인구통계 세부정보 → 국가 |
| 언어별 · 페이지별 관심 | 보고서 → 참여 → 페이지 및 화면(`/vi/`, `/en/` 등 경로로 검색) |
| 카탈로그 PDF 다운로드 | 보고서 → 참여 → 이벤트 → `file_download` |
| 박람회 당일 QR 스캔이 들어오는지 | 보고서 → **실시간**(지난 30분) |
| 특정 문의 한 건의 경로 | 탐색 → 자유 형식. 측정기준 "접수 번호" + "세션 소스/매체" + "방문 페이지" |

**주의**

- GA4는 광고 차단 · 추적 거부 브라우저를 세지 못해 실제보다 적게 나옵니다. 문의 건수의 정답은 메일(또는 영업 시트)입니다. GA4는 비율과 추세로 봅니다.
- 문의가 적은 달에는 전환율이 크게 흔들립니다. 분기 단위로 봅니다.

## 6. 영업 결과 기록(시트)

문의가 계약으로 이어졌는지는 사이트가 알 수 없습니다. 담당자가 공유 시트에 한 줄씩 적으면, 접수 번호로 메일 · GA4와 이어져 "어느 홍보가 계약을 만들었나"까지 보입니다.

| 접수 번호 | 접수일 | 기관 | 목적 | 제품 | 이번 유입 | 첫 방문 | 유입 경로(응답) | 단계 | 금액 | 메모 |
|---|---|---|---|---|---|---|---|---|---|---|
| WS-261015-7K2Q | 2026-10-15 | Hanoi University | 시연 요청 | LearnHubble AI | fair / print / vietedu-2026 | google / organic | 박람회·행사 | 시연 | | |

- 앞의 여덟 칸은 메일의 접수 정보를 옮겨 적습니다.
- 단계: 접수 → 상담 → 시연 → 제안 → 계약(또는 보류 · 종료).
- 한 달에 한 번: 채널 · 캠페인별로 문의 수, 시연 수, 계약 수를 세어 봅니다. 홍보 예산을 어디에 더 쓸지 여기서 정합니다.
- 개인정보처리방침대로 문의는 1년 보관 뒤 파기합니다. 시트의 이름 · 연락처 칸도 같이 지웁니다(분석에는 기관 · 유입 칸만 있으면 됩니다).

## 7. 개인정보

- 브라우저에 남기는 유입 기록에는 개인을 알아볼 정보가 없습니다. 문의를 보낼 때만 메일에 함께 실려 회사로 옵니다.
- GA4로는 이름 · 이메일 · 소속 · 문의 내용을 보내지 않습니다(자동 점검이 확인합니다: `tests/behavior.spec.ts` 문의 폼).
- 개인정보처리방침 1 · 2 · 7 · 13항에 방문 경로 정보를 적었습니다(시행일 2026-10-13). 방침에 따라 시행 7일 전(10.6)까지 지금 사이트에 변경을 공지합니다.

## 8. 다음 단계(서버를 고칠 때)

지금은 문의 서버(Lambda)를 그대로 쓰므로 접수 정보가 메일 본문의 글로 옵니다. 서버 코드를 고칠 수 있게 되면:

- 서버가 메일과 함께 문의를 표(DynamoDB 등)로 저장하고, 1년이 지나면 자동으로 지웁니다.
- 관리 화면에서 CSV로 내려받아 6장 시트를 손으로 옮기지 않아도 되게 합니다.
- 그때 폼이 접수 정보를 글 대신 따로 된 값으로 보냅니다(`attribution()`이 이미 모든 값을 갖고 있습니다).
